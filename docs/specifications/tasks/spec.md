DayMark Tasks — Unified Specification
Status: Requirements consolidation; unresolved business rules must be approved before implementation
Backend: FastAPI REST API | Database: PostgreSQL (SQL) | State: Bloc/Cubit | Navigation: GoRouter | Architecture: Clean Architecture

1. Authority and Scope
   This is the single source of truth for task data, task creation/retrieval/editing, task lifecycle and status transitions, completion/reopening, deletion/archive, filtering, sorting, grouping, date-based task queries, categories, and task-level reminder configuration.
   Precedence: system/safety → global DayMark rules → this SPEC → relevant skills → current task prompt. Lower levels may clarify but cannot weaken higher levels. Surface conflicts; never silently alter approved requirements.

The Task feature owns task records and task-level business rules. Dashboard, Calendar, and Productivity/Insights consume Task data and must not duplicate task validation, lifecycle, or task-query rules. Reminder and notification preferences are owned by Profile and notification infrastructure, not Tasks. 2. Functional Requirements

3. Task Data Contract
   A task contains:
   Field Requirement
   Task ID Unique identifier generated by the approved persistence layer.
   Owner/User ID Associates task with its owner; not editable by the user.
   Title Required.
   Description Optional.
   Start Date Supported; exact optional/required behavior must be approved.
   Due Date Supported; exact optional/required behavior must be approved.
   Start Time Optional.
   End Time Optional.
   Priority Low, Medium, High, Urgent.
   Category Associated category; required/optional behavior must follow approved contract.
   Status Pending, In Progress, Completed, Cancelled.
   Subtasks Optional; behavior follows approved Subtask contract.
   Task Reminder Optional; task-associated reminder configuration follows approved reminder contract.
   Recurrence Optional; behavior follows approved Recurrence contract.
   Completed At Completion timestamp; set/cleared according to lifecycle transitions.
   Created At Persistence-generated creation timestamp.
   Updated At Updated when task data changes.
   Archived/Deleted state Only if archive/deletion policy is approved and implemented.
   Do not add fields such as attachment metadata, location, tags, estimated duration, or custom priority/status values unless approved. 4. Create and Read
   Create

- Provide task creation with required title and supported optional fields.
- Validate input before submitting.
- Prevent duplicate submissions while request is in progress.
- On success, use the persisted task record as source of truth.
- Creation failure must not display success or create a phantom task.
- Initial status must follow the approved default-status rule; do not assume a value without confirmation.
  Read / List
- Retrieve task details by task identifier with ownership enforced.
- Retrieve task collections for supported date ranges and views.
- Support refresh/reload.
- Handle loading, empty, success, and failure states.
- Queries must respect current-user ownership and approved filters.

5. Update and Delete/Archive
   Update
   - Edit supported task fields.
   - Re-run applicable validation.
   - Preserve fields not explicitly changed.
   - Apply lifecycle constraints to status/completion changes.
   - Handle concurrent/stale updates according to persistence strategy; do not silently overwrite newer data if conflict handling is supported.
   - If reminder-related task data changes, notify the shared notification service so its schedule can be reconciled.
     Delete / Archive
   - Provide the approved destructive action with appropriate confirmation.
   - Distinguish permanent deletion from archive if both are supported.
   - Do not invent soft-delete behavior, retention, or restoration rules.
   - Ensure deleted/archived tasks are excluded from queries according to approved policy.
   - Report success only after persistence confirms the operation.
   - Deletion/archive must trigger reminder cancellation through the shared notification service when applicable.
6. Status Lifecycle and Transitions
   Supported statuses:
   - Pending
   - In Progress
   - Completed
   - Cancelled
     The feature must enforce an explicit transition matrix. Any proposed matrix must be approved before implementation.
     Completion timestamp behavior, reopening behavior, whether completed/cancelled tasks may be edited, and whether cancellation is reversible remain approval-dependent. Do not silently choose these rules. 7. Validation and Date/Time Rules
     Validation must cover:

- Required title and approved length/whitespace rules.
- Supported enum values.
- Identifier validity.
- Start/due-date relationship.
- Start/end-time relationship and date/time combinations.
- Applicable category selection.
- Reminder configuration validity.
  Exact rules not yet approved must remain explicitly unresolved. Do not invent limits, date constraints, defaults, or timezone assumptions.

8. Categories
   8.1 Built-in Categories
   The application provides these default categories:
   - Work
   - Study
   - Personal
   - Health
   - Fitness
   - Shopping
   - Finance
   - Other
     8.2 Custom Categories
     Users can:
   - Create custom categories.
   - Edit custom category names/details that are approved.
   - Delete custom categories.
     8.3 Category Ownership and Integrity
   - Category records must be associated with the authenticated user or represented through an approved shared/default-category strategy.
   - Users must not access or modify another user's custom categories.
   - Task-category associations must use the authoritative category record/identifier.
   - Duplicate-name behavior, case sensitivity, trimming/normalization, and whether custom categories may match built-in names require approval.
   - Built-in categories must be protected from user deletion or modification unless an explicit approved policy permits it.
   - Deleting a category currently referenced by tasks must follow an approved policy (e.g., block deletion, reassign, or remove association). Do not choose silently.
   - Category changes must not corrupt task records or leave invalid references.
     8.4 Category UI and States
     Category management must support applicable loading, empty, success, and failure states. Creating/editing/deleting must not report success before persistence is confirmed.
9. Subtasks and Recurrence Boundaries
   Subtasks
   - A task may have optional subtasks.
   - Define independent status, dates, priority, completion timestamp, parent-completion dependency, limits, nesting, ordering, edit, and delete behavior before implementation.
   - Parent/subtask lifecycle rules require approval.
     Recurrence
   - A task may have optional recurrence.
   - Recurrence patterns, end conditions, generated-instance identity, editing one occurrence versus a series, skipped occurrences, timezone, and generation strategy must be approved.
   - Do not generate recurring task copies without a defined contract.
10. Architecture and Ownership - Presentation: task UI, forms, lists/details, filters/sort/group controls, category UI, reminder configuration UI, Bloc/Cubit. - Domain: task/category entities, approved business rules, validation, lifecycle transitions, use cases, repository contracts. - Data: FastAPI REST API integration, DTO/model mapping, queries, and data-source error handling; approved local persistence where required. - Repository: abstracts persistence and returns project-owned Result/Failure types. - DataSource: maps provider failures to application-owned errors; provider exceptions must not leak to Presentation. - Notification Service: shared infrastructure owns permission handling, scheduling, rescheduling, cancellation, and platform-specific delivery.
    Follow existing project conventions. Inspect repository before creating/modifying files; do not introduce a parallel architecture.
    Backend and Database Boundaries

- Flutter must communicate with the backend through REST APIs exposed by FastAPI.
- Flutter must not connect directly to PostgreSQL or contain database credentials.
- FastAPI owns request validation, authorization, task/category orchestration, and database access.
- PostgreSQL must use appropriate constraints, foreign keys, indexes, and parameterized SQL.
- Database schema changes must follow the project's established migration process.
- Task and custom-category ownership must be enforced by backend authorization and database integrity mechanisms as applicable; never trust client-supplied owner IDs.
- Task, category, recurrence, subtask, and reminder persistence must follow their approved feature contracts and ownership boundaries.
- Task lifecycle changes that affect reminders must coordinate with the shared Notification Service; scheduling/delivery logic must not be duplicated in Task.
- Do not introduce or assume a specific ORM, migration tool, endpoint, request/response format, authentication/token implementation, schema, or transaction strategy unless confirmed by the existing project or an approved specification.
- Flutter may use local persistence only where the approved architecture requires it; it must not become an alternative source of truth for backend-owned task data.

12. Data Integrity, Security, and Reliability
    - Every task and custom category must be associated with the authenticated owner as applicable.
    - Users must not read, update, delete, or archive another user's records.
    - Enforce ownership at backend/database policy level, not only UI.
    - Do not trust client-supplied owner IDs.
    - Validate enums, identifiers, and constraints at appropriate boundaries.
    - Avoid logging sensitive task data unnecessarily.
    - Prevent duplicate submissions where applicable.
    - Handle network failures without falsely reporting persistence success.
    - Use approved FastAPI authorization rules and PostgreSQL schema/constraints; verify actual configuration rather than inventing it.
    - Follow global security, privacy, logging, dependency, and release rules.

    - Dashboard, Calendar, and Insights consume task data and must not duplicate task rules.
    - Task feature must not duplicate profile preferences or notification infrastructure.
